# 동아리 생성

## 화면과 계약

2026-11-03(KST)에 Backend `98441b9`의 OpenAPI 0.1.0·Clubs 컨트롤러·생성 e2e 계약을 확인했다. 기획 v4 `06-club-create`·`07-club-created`의 크림색 입력 카드, 파트별 색상과 완료 후 큰 초대 코드 표시를 참고했다. 기존 하늘색·네이비 테두리·노란 주요 버튼과 공통 컴포넌트를 사용한다.

가입·신청 화면의 `새 동아리 만들기`에서 `/clubs/create`를 연다. 인증이 필요한 루트 Stack 화면이며 하단 탭은 없다. 동아리 이름, 한 개 이상의 파트와 색상, 생성자의 소속 파트를 입력한다. 동아리명은 앞뒤 공백 제거 후 1~20 grapheme, 파트명은 1~10 grapheme이며 같은 이름의 파트를 허용하지 않는다. 내 소속은 현재 남아 있는 파트 중 하나여야 한다. 선택한 파트를 삭제하면 선택을 해제하고, 이름을 바꾸면 현재 이름을 전송한다. 파트 수를 시안의 임의 7개로 제한하지 않는다. `Intl.Segmenter`가 없는 런타임의 길이는 서버 검증을 따른다.

| 요청 | 용도 |
| --- | --- |
| `POST /clubs` | `{ name, parts: [{ name, color }], myPartName }`만 전송 |
| `GET /clubs/{clubId}` | 저장된 생성 결과의 현재 이름·초대 코드 재조회 |
| 기존 내 부원 목록과 동아리 조회 | 공지로 이동하기 전 실제 부원 자격 확인 |

생성자 운영진 역할과 기본 `전체공지` 분류는 서버가 생성한다. 시안의 “파트와 같은 이름의 공지 분류 자동 생성”은 실제 계약과 달라 추가하지 않았다. 이름의 시안 제한 16자도 계약의 20자로 맞췄다. 출석·공부·보상 규칙을 수정하는 항목은 없다.

## 결과와 재전송

`POST /clubs`에는 idempotency key 계약이 없다. 따라서 중복 탭은 직렬 처리하고, **전송 전에** 계정별 생성 의도를 저장한다. 저장에 실패하면 POST하지 않는다. 성공 응답의 UUID·이름·부원 수·시각·초대 코드 형식을 검증하고, 확인된 동아리 ID를 저장한다. API 모드의 기록에는 초대 코드·토큰·입력한 이름·연락처를 저장하지 않는다.

키는 `@tamagochi/club-create-intent/v1/{API 주소}/{사용자 ID}`다. 기존 계정 scope와 고정 Bearer 토큰을 사용하므로 다른 계정의 기록이나 지연 응답이 현재 화면에 적용되지 않는다. 생성 전에 남긴 pending 기록이 있으면 재실행 후에도 POST를 자동 재전송하지 않는다.

이 기록은 해당 기기의 재전송을 막는다. 다른 기기나 브라우저에서 동시에 보낸 별도 생성 요청까지 하나로 합치는 서버 계약은 없다.

- 정상 결과는 현재 서버 정보를 조회해 표시한다. 코드가 응답에 없으면 만들거나 이전 코드를 대신 표시하지 않는다. 코드는 선택·길게 누르기로 복사할 수 있다.
- 네트워크·타임아웃·5xx·잘못된 성공 응답은 생성 여부가 불확실하다. 가입 목록에서 실제 동아리를 확인하도록 안내한다. 상태 다시 확인은 읽기만 한다. 이름이 같다는 이유로 동아리를 새 생성 결과라고 추정하지 않는다.
- 사용자가 가입 목록을 확인한 뒤 명시적으로 새로 작성할 수 있다. 이때 기존 요청은 취소되지 않으며 중복 동아리가 생길 수 있다는 안내와 별도 확인을 표시한다. 기록 초기화 자체는 서버 요청이나 동아리 삭제를 하지 않는다.
- 확정된 400·401·403 등 요청 거절은 의도 기록을 해제하고 오류를 표시한다. 입력값은 유지하며 자동으로 다시 보내지 않는다. 기록 해제에 실패하면 새 요청을 막는다.
- 성공 응답 뒤 ID 저장만 실패해도 현재 확인한 결과는 표시한다. 기존 pending 기록은 남아 있어 재실행 시 안전하게 결과 확인 화면으로 돌아온다.
- 저장소 읽기 실패·손상은 데이터를 지우거나 새 기록으로 덮지 않는다. 결과 조회가 불가능하면 읽기 재시도와 가입 목록 확인을 제공한다.

공지 이동 직전 생성 결과·현재 부원 목록을 다시 읽고 공통 동아리 선택 저장 성공까지 확인한다. 권한 회수나 선택 저장 실패 시 이전 동아리로 이동하지 않는다. 초대 코드 조회 실패 시 기존 코드도 화면에서 내린다. 화면을 나가거나 뒤로 가는 동작은 이미 전송한 생성 요청을 취소하지 않는다.

## Mock

`@tamagochi/mock-created-clubs/v1`에 만든 동아리·파트·내 소속·8자리 코드를 저장한다. `@tamagochi/mock-club-create-intent/v1`은 별도의 재전송 방지 기록이다. 기존 공부·목표·상점·가입 신청·공지 읽음 저장소를 수정하지 않는다.

생성한 동아리는 기존 가입·공지와 동일한 부원 목록에서 조회된다. 생성자는 이미 부원이므로 코드 조회 후 가입 신청을 추가하지 않는다. 새 동아리의 공지는 `전체공지` 분류만 있고 글과 읽지 않은 수는 0이다. 기존 데모 동아리의 공지·신청 동작은 유지한다. 코드 생성은 로컬 미리보기 전용이며 실제 API 모드에서는 서버 코드만 사용한다.

## 실행과 검증

```powershell
npm.cmd run typecheck
npm.cmd run lint -- --no-cache
npm.cmd test
```

새 라우트 타입은 공식 `npx.cmd expo customize tsconfig.json`으로 갱신했다. 생성 타입을 직접 수정하거나 타입 단언으로 우회하지 않았다. 구현을 확인할 때 아래처럼 내보낸 Mock Web 빌드를 사용할 수 있다.

타입·린트와 총 114개 테스트를 통과했다. 새 14개는 grapheme·중복 파트·생성자 소속 검증, 요청 본문, 전송 전 의도 저장·중복 차단, 응답 유실·확정 거절·잘못된 영수증, 저장소 실패와 복구·계정별 기록, Mock 부원 자격·빈 기본 공지·공부 저장소 보존을 검증한다. Android·iOS·Web 번들도 통과했다.

격리 Chrome에 API 응답을 주입해 인증 전 차단, 파트 편집·선택 삭제, 중복 클릭, 새로고침·현재 초대 코드, 선택 저장 실패, 실제 부원 확인 후 공지 진입, 응답 유실·재실행·명시적 새 작성, 400·저장 실패·권한 회수·계정 전환·401 만료를 확인했다. 320·390·1280px에서 가로 넘침도 확인했다. Mock에서는 생성 복구·코드 조회·가입/공지 목록 공유, 빈 전체공지, 저장 실패 후 명시적 새 작성, 여러 동아리 생성과 기존 공부 기록 보존을 확인했다. 기존 Mock 가입·취소·승인 결과 후 공지 진입도 다시 통과했다. 운영 API 쓰기는 하지 않았다.

```powershell
$env:EXPO_PUBLIC_DATA_MODE='mock'
npx.cmd expo export --platform web --output-dir .expo/preview
npx.cmd expo serve .expo/preview --port 8082
```

`http://localhost:8082/clubs/create`에서 로그인 없이 미리 볼 수 있다. 실제 API 모드는 `EXPO_PUBLIC_DATA_MODE=api`로 다시 내보내고 인증한다. 실계정 생성·다른 기기와의 동시 처리·운영진 관리·실기기 키보드 및 화면 읽기 검증은 별도다. 운영진의 가입 승인/거절, 권한 관리, 동아리 탈퇴 화면은 이번 범위가 아니다.
