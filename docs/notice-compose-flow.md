# 운영진 공지 작성

## 화면과 계약

2026-11-03(KST)에 Backend `98441b9`의 OpenAPI 0.1.0, Notices 컨트롤러·도메인·e2e 계약을 확인했다. 기획 v4 `18-compose`의 분류·세부 분류 칩, 크림색 입력 영역, 제목·긴 본문, 고정·알림 토글과 상단 노란 등록 버튼을 참고했다. 제목은 1~50자, 본문은 시안의 500자가 아닌 계약의 1~2,000 grapheme cluster다. 앞뒤 공백만 제거하고 본문 줄바꿈은 유지한다. `Intl.Segmenter`가 없는 런타임에서는 최대 길이를 서버가 검증한다.

공지의 현재 선택 동아리에 `notices.write` 권한이 있으면 `+` 아이콘(접근성 이름은 `동아리명 공지 쓰기`)을 표시한다. 톱니바퀴의 공지 설정에서도 같은 기능을 열 수 있다. [최신 탐색 구조](ui-refinement.md)를 따른다. 클릭 직전에도 권한을 확인하며 `/clubs/{clubId}/notices/compose`를 연다. 인증이 필요한 루트 Stack 화면으로 하단 탭은 없다. 직접 주소로 들어와도 권한 확인을 통과해야 동아리·분류와 이전 등록 결과를 조회한다. 가입 신청 관리 권한만으로는 공지를 쓸 수 없다.

| 요청 | 용도 |
| --- | --- |
| `GET /clubs/{clubId}/members/me/permissions` | 진입·상태 확인·등록 직전의 현재 권한 확인 |
| `GET /clubs/{clubId}`, `/noticeCategories` | 작성 대상과 동적 분류·세부 분류 |
| `POST /clubs/{clubId}/notices` | `{ categoryId, subcategoryId?, title, body, pinned, notify }`만 전송 |
| `GET /clubs/{clubId}/notices/{noticeId}` | 확인된 공지와 현재 알림 발송 상태 복구 |

첫 분류를 기본 선택하며, 분류를 바꾸면 세부 분류를 해제한다. 세부 분류는 선택하지 않을 수 있고 이때 전송 필드에서 뺀다. 고정·알림의 기본값은 서버와 같은 false다. 등록 직전에 분류를 다시 읽어 삭제·이동 여부를 확인한다. 변경되었으면 입력을 유지하고 재선택을 안내한다. 빈 분류에서는 등록하지 못한다. 시안처럼 고정된 분류명이나 알림 수신 인원을 만들지 않는다.

등록 버튼은 입력 영역과 별도로 상단에 있어 본문을 스크롤해도 이용할 수 있다. 입력 오류는 수정하면 내리고, 저장 실패에서는 입력을 유지한다. 화면 진입·앱 활성화·직접 재확인은 분류와 권한을 조회하지만 작성 중인 내용을 덮지 않는다. 권한 상실·인증 만료가 확인되면 내용과 등록 결과를 내린다. 작성 중 이탈은 확인하며, 임시 본문 저장 기능은 추가하지 않았다.

## 등록 요청과 복구

POST에는 idempotency key 계약이 없다. 중복 탭을 화면과 서비스에서 막고, 전송 전에 계정·동아리별 요청 기록을 저장한다. 저장에 실패하면 POST하지 않는다. 성공 응답의 ID·본문·분류·고정·알림 상태를 검증하며 요청과 다른 영수증은 성공으로 확정하지 않는다.

API 기록 키는 `@tamagochi/notice-create-intent/v1/{API 주소}/{사용자 ID}/{동아리 ID}`다. pending 기록에는 요청 식별자만, 확인된 결과에는 공지 ID만 저장한다. 제목·본문·토큰·알림 수신자 목록은 보관하지 않는다. 다른 계정이나 동아리의 기록을 복구하지 않으며, 다른 탭의 새 pending 요청에 이전 메모리 영수증을 적용하지 않는다.

- 확인된 결과는 공지 ID로 다시 조회한다. ID 저장만 실패해도 현재 확인된 결과를 보여주며, 재실행 시 남은 pending 기록이 반복 등록을 막는다.
- 네트워크·타임아웃·5xx·잘못된 성공 응답에서는 등록 여부가 불확실하다. 새로고침·재실행·상태 다시 확인은 POST를 반복하지 않는다. 제목이나 내용이 같다는 이유로 목록의 공지를 내 요청 결과라고 추정하지 않는다.
- 불확실한 결과는 공지 목록에서 확인한다. 사용자가 명시적으로 새 작성을 선택하면 이전 요청이 취소되지 않고 공지·알림이 중복될 수 있다는 안내 후 로컬 요청 기록을 초기화한다. 이 초기화는 서버의 공지를 지우지 않는다.
- 확정된 400·401·403·404·422 거절은 요청 기록을 해제한다. 입력은 유지하고 자동 재전송하지 않는다. 해제 저장에 실패하면 기존 pending 기록이 남아 재전송을 막는다.
- 요청 기록 읽기 실패·손상은 기존 데이터를 지우거나 덮어쓰지 않는다. 저장된 공지가 삭제되어 조회할 수 없는 경우에도 목록 확인과 명시적인 새 작성이 필요하다.

이 기록은 한 서비스 안의 중복 요청과 기기 재실행을 다룬다. 다른 기기·브라우저에서 동시에 보낸 별개 POST까지 하나로 합치는 서버 계약은 없다. 기존 계정 scope와 고정 Bearer 클라이언트를 사용해 늦은 응답을 다른 계정에 적용하지 않는다.

## 결과·알림·목록

등록 결과는 제목·본문과 서버의 `notificationState`를 표시한다. `NONE`은 알림 요청 없음, `PENDING`은 발송 대기, `SENT`는 서버 발송 완료, `FAILED`는 공지는 등록됐으나 발송 실패다. 상태 다시 확인은 현재 공지와 권한·분류를 조회하며 알림을 재발송하지 않는다. 자동 폴링이나 실제 기기 수신 성공 표시는 추가하지 않았다.

공지 목록으로 이동할 때 현재 부원 목록과 동아리 선택 저장을 확인한다. 목록은 화면 재진입 시 최신 글·고정 순서·읽지 않은 전체 수를 조회한다. 등록 자체는 읽음 처리를 하지 않으며, 기존처럼 본문을 펼칠 때 읽음을 전송한다. 후속 [공지 수정·삭제](notice-management-flow.md)도 같은 권한과 입력 컴포넌트에 연결했다. 실제 푸시 수신·FCM 토큰 연동은 후속 범위다.

## Mock과 검증

첫 동아리와 직접 만든 동아리에는 `notices.write` 권한이 있고, 두 번째 동아리는 일반 부원이다. 권한 데이터는 기존 가입 신청 관리와 같은 Mock 서비스에서 제공한다. 생성한 동아리의 공지는 전체공지 분류만 있는 빈 목록에서 시작한다.

새 공지는 `@tamagochi/mock-notice-content/v1`, 등록 요청은 `@tamagochi/mock-notice-create/v1/{동아리 ID}`에 저장한다. 기존 공지 목록·분류 필터·읽음 저장소를 함께 사용해 등록 후에도 결과가 일치한다. 기존 공부·상점·가입 신청 기록은 수정하지 않는다. 알림 요청은 PENDING으로 저장하며 실제 푸시를 보내거나 수신 완료로 자동 전환하지 않는다. 저장 실패·손상 시 기존 기록을 보존한다.

타입 검사·린트, 총 166개 테스트가 통과했다. 새 18개는 grapheme·공백·줄바꿈, 권한 선확인, 동적 분류·삭제된 세부 분류, 정확한 요청, 전송 전 기록·중복 차단, 거절·응답 유실·잘못된 영수증·저장 실패, 공지 ID 복구·발송 상태, 계정·동아리·다른 탭의 요청 격리, Mock 목록·읽음·새 동아리와 공부 기록 보존을 검증한다. API Android·iOS·Web과 Mock Web 내보내기도 통과했다.

별도 프로필의 숨김 Chrome에 가짜 API를 주입해 로그인·권한별 진입, 입력 검증·분류 전환, 이탈 확인, 중복 탭·저장 실패·재실행, 현재 알림 상태, 목록·읽지 않은 수·본문 읽음, 400·등록 응답 유실·잘못된 응답·결과 저장 실패, 분류 삭제·권한 회수·계정 전환·401을 확인했다. 320·390·1280px의 가로 넘침과 상단 등록 버튼의 스크롤 후 위치를 확인했다.

Mock 브라우저에서도 등록 복구·필터·읽음, 저장 실패 후 목록 확인·명시적 새 작성, 일반 부원 차단, 새 동아리 공지 작성과 기존 공부 기록 보존을 확인했다. 브라우저의 운영 API 네트워크를 차단했고 Mock의 운영 API 호출도 0회였다. 실제 운영 공지 등록·알림 발송, 여러 기기의 동시 등록과 실기기 키보드·화면 읽기 검증은 별도다.

```powershell
$env:EXPO_PUBLIC_DATA_MODE='mock'
npx.cmd expo export --platform web --output-dir .expo/preview
npx.cmd expo serve .expo/preview --port 8082
```

`http://localhost:8082/notice`에서 첫 동아리의 `+ 공지 쓰기`를 누르거나 `/clubs/mock-club-study/notices/compose`로 직접 연다. API 모드는 `EXPO_PUBLIC_DATA_MODE=api`로 다시 내보내고 실제 작성 권한이 있는 계정으로 로그인한다.
