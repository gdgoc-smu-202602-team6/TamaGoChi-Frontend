# 동아리 파트 관리

## 화면과 계약

2026-11-04(KST)에 Backend `98441b9`의 Parts 컨트롤러·저장소, Label 도메인·e2e와 OpenAPI 0.1.0을 확인했다. v4 `24-club-admin`의 색상별 파트 칩·입력 카드·추가 버튼을 참고해 하늘색 배경, 크림색 카드, 네이비 외곽선과 노란 주요 버튼을 재사용한다. 기존 `GameColorPicker`, 입력·버튼·확인창을 사용하며 새 패키지는 추가하지 않았다.

공지와 마이의 선택 동아리, 동아리 기본 설정에서 `파트 관리`를 연다. `parts.manage` 권한을 독립적으로 검사하므로 `club.update`, `members.manage`, `applications.decide`만으로는 관리할 수 없다. 기본 설정 권한이 없어도 공지·마이에서 파트 관리 권한으로 직접 들어갈 수 있다. `/clubs/{clubId}/parts`는 인증이 필요한 루트 Stack 화면이며 하단 탭은 없다. 버튼 클릭·화면 진입·foreground 복귀·변경 직전·결과 조회 때 권한을 다시 확인한다.

| 요청 | 용도 |
| --- | --- |
| `GET /clubs/{clubId}/members/me/permissions` | 현재 파트 관리 권한 |
| `GET /clubs/{clubId}` | 현재 동아리 이름·부원 수 |
| `GET /clubs/{clubId}/parts` | 전체 파트 ID·이름·색상 |
| `POST /clubs/{clubId}/parts` | `{ name, color }`로 추가 |
| `DELETE /clubs/{clubId}/parts/{partId}` | 본문 없이 삭제 |

이름은 앞뒤 공백 제거 후 1~10 grapheme cluster이며 같은 동아리 안에서 중복될 수 없다. `Intl.Segmenter`가 없으면 최대 길이는 서버가 검증한다. 색상은 계약의 여덟 값이다. 이름·색상 변경과 순서 변경 API는 없어 추가하지 않았다.

부원이나 승인 대기 신청이 사용하는 파트는 서버가 409 `in-use`로 거절한다. 기본 파트라는 별도 속성이나 “최소 한 개” 규칙은 클라이언트에서 만들지 않는다. 삭제는 이름을 확인한 뒤 실행하며, 확인 당시 원본을 보관해 중간 재조회가 확인 대상을 바꾸지 않도록 한다. 실행 직전 이름·색상이 달라졌으면 쓰지 않고 다시 선택하도록 한다. 이미 없으면 DELETE 없이 현재 목록을 반영한다.

## 실패·결과·격리

중복 탭은 화면과 서비스에서 직렬화한다. 추가·삭제 뒤 권한과 목록을 다시 읽어 실제 상태를 확인한다. 409 `duplicate-name`·`in-use`와 확정된 4xx는 쓰기를 반복하지 않고 입력과 최신 목록을 제공한다. 네트워크·타임아웃·5xx·잘못된 성공 응답·삭제 404도 목록을 조회해 확인한다.

추가한 이름·색상이 있거나 삭제한 ID가 없는 상태를 확인하면 “현재 파트 목록에서 처리 상태를 확인했어요”로 안내한다. 다른 운영진이 만든 상태일 수 있어 내가 처리했다고 추정하지 않는다. 결과를 확인하지 못하면 마지막 목록과 입력을 유지하고 변경 기능을 잠근다. `파트 목록 다시 확인`은 GET만 보내며, 새 목록을 검토한 사용자가 다음 작업을 명시적으로 선택한다. 자동 POST/DELETE 재시도는 없다.

서버에는 파트 변경의 ETag·조건부 삭제·idempotency key 계약이 없다. 사전 비교 이후의 동시 변경까지 원자적으로 막는 동작을 보장하지 않는다. API 모드의 입력·목록·미확정 요청은 AsyncStorage에 저장하지 않고 재실행 시 현재 목록만 읽는다. 화면을 벗어나면 저장하지 않은 이름 입력은 유지하지 않는다. 권한 상실·인증 만료 시 목록·입력·열린 확인창을 제거한다. 계정별 서비스 scope와 고정 Bearer 클라이언트로 다른 계정의 늦은 응답을 적용하지 않는다.

`◀ 공지`와 `공지 목록으로`는 현재 소속과 동아리 선택 저장을 확인하고 이동한다. 파트를 변경해도 공지 분류·동아리 이름·초대 코드·공부 상태는 수정하지 않는다.

## Mock과 검증

Mock은 `@tamagochi/mock-club-parts/v1`의 `{ version: 1, clubs: { [clubId]: parts } }`에 동아리별 목록을 저장한다. 기록이 없으면 기존 카탈로그나 생성한 동아리의 파트를 복제해 읽으며 조회만으로 저장하지 않는다. 가입 검색·신청 시 검증·신청의 파트 표시·운영진 승인 대기 화면이 같은 동적 목록을 사용한다. API 오류를 Mock으로 전환하지 않는다.

미리보기의 부원 소속은 후속 [부원·역할 관리](club-member-roles-flow.md)와 같은 부원 목록으로 보호한다. 추가로 내 신청과 운영진 대기/승인 기록의 참조를 검사한다. 거절한 신청만 남아 있으면 삭제할 수 있다. 삭제된 파트를 참조하는 결정 완료 신청은 조회 모델에서 `partId: null`로 표시하고 원본 기록·결정일은 수정하지 않는다. 다른 동아리·기존 신청·공부·공지 기록은 변경하지 않는다. 손상과 저장 실패는 기존 기록을 지우거나 성공으로 확정하지 않는다.

타입·린트와 총 244개 테스트가 통과했다. 새 19개는 정확한 권한·DTO·입력·색상, 요청 본문·중복 탭·원본 변경·삭제 404, 확정 거절·응답 유실·잘못된 성공 응답·미적용·재조회 실패·권한 회수, Mock 가입/승인 목록 공유·부원/생성자/대기/승인 참조·거절 후 해제·저장 실패·손상 보존을 검증한다. API Android·iOS·Web과 Mock Web 내보내기도 통과했다.

격리 Chrome의 가짜 API로 인증 전 접근 제한·독립 권한, 이름·색상·중복 추가, 사용 중 삭제 제한·취소·확인 중 변경, 응답 유실·잘못된 응답·늦은 재조회·명시적 재시도, 계정 전환·권한 회수 시 확인창 제거·인증 만료를 확인했다. Mock에서는 새 파트 저장·재실행·중복 쓰기 방지, 실제 대기 신청과 파트 표시 공유·거절 후 삭제, 저장 실패 후 입력 보존, 외부 운영자가 추가한 파트로 가입 신청, 생성자 파트 보호·새 동아리 운영자·동아리 격리·공부 기록 보존을 확인했다. 320·390·1280px에서 가로 넘침을 확인했다. 공유 Mock 변경 후 기존 가입 신청 승인·거절 브라우저 검증도 통과했다.

운영 API 네트워크를 차단한 환경에서 검증했으며 운영 파트를 추가하거나 삭제하지 않았다. 실계정의 부원/신청 동시 처리, 실기기 키보드·화면 읽기 검증은 별도다.

미리보기는 `http://localhost:8082/notice`의 첫 동아리에서 `파트 관리`를 누른다. 직접 주소는 `/clubs/mock-club-study/parts`다. 두 번째 Mock 동아리에는 권한이 없어 버튼이 없다. 실제 API에서는 `parts.manage` 권한이 필요하다.
