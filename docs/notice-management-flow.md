# 공지 수정·삭제

## 화면과 권한

2026-11-03(KST)에 Backend `98441b9`의 OpenAPI 0.1.0, Notices 컨트롤러와 도메인·e2e 계약을 확인했다. 기존 공지 카드와 v4 `18-compose`의 크림색 입력 영역, 분류 칩·고정 토글과 상단 노란 버튼을 재사용한다. 공통 입력은 `NoticeFields`, 확인창은 `GameConfirmDialog`로 분리했다. 제목·본문 길이와 grapheme·공백·줄바꿈 기준은 공지 작성과 같다.

본문을 펼친 공지에 `notices.write` 권한이 있으면 `수정·삭제`를 표시한다. 작성자 본인 여부가 아닌 서버 권한으로 관리한다. 버튼을 누를 때 다시 확인하고 `/clubs/{clubId}/notices/{noticeId}/edit`를 연다. 직접 주소 접근도 인증·현재 권한 확인 후 정확한 공지를 조회한다. 일반 부원과 가입 신청 관리 권한만 있는 부원에게는 관리 기능을 제공하지 않는다.

수정 화면에는 분류·세부 분류·제목·본문·고정과 현재 알림 상태를 표시한다. 저장 버튼은 스크롤 영역 밖에 있다. 수정 시 알림을 재발송하지 않으므로 발송 토글을 넣지 않는다. 이 화면의 조회 자체는 읽음을 보내지 않는다. 공지 카드의 본문을 펼칠 때 저장하는 기존 읽음 동작은 유지한다.

## API와 변경 확인

| 요청 | 용도 |
| --- | --- |
| `GET /clubs/{clubId}/members/me/permissions` | 진입·재확인·저장·삭제 직전 권한 확인 |
| `GET /clubs/{clubId}`, `/noticeCategories` | 현재 동아리와 동적 분류 |
| `GET /clubs/{clubId}/notices/{noticeId}` | 편집 원본과 처리 직전·응답 유실 후 상태 |
| `PATCH /clubs/{clubId}/notices/{noticeId}` | 달라진 `categoryId`, `subcategoryId`, `title`, `body`, `pinned`만 전송 |
| `DELETE /clubs/{clubId}/notices/{noticeId}` | 본문 없이 삭제 |

최신 OpenAPI는 `NoticeUpdate.subcategoryId`에 null을 허용한다. 같은 분류 안에서도 `선택 안 함`으로 해제하면 `subcategoryId: null`을 보내며, 필드를 생략하는 “유지”와 구분한다. 분류를 바꾸면 선택을 해제한다. 저장 직전 현재 분류 관계를 검사하고 삭제·이동된 항목은 다시 선택하도록 한다.

저장·삭제 직전의 공지를 마지막으로 확인한 원본과 비교한다. 다른 내용으로 바뀌었으면 쓰기 요청을 보내지 않고 현재 내용을 확인하도록 안내한다. 알림 상태의 비동기 변경과 읽음은 본문 충돌로 취급하지 않는다. 이미 입력한 내용과 같으면 추가 PATCH 없이 현재 공지를 반환한다. 작성자·생성일·읽음·알림 필드는 PATCH에 보내지 않는다.

삭제는 공지 제목과 복구할 수 없다는 안내를 확인한 뒤 실행한다. 확인창을 열었을 때의 원본을 유지하므로, 확인창이 열린 동안 foreground 재조회로 새 내용을 받았더라도 이전 내용에 대한 확인으로 새 공지를 삭제하지 않는다. 권한이 사라지면 본문·초안과 열린 확인창도 함께 제거한다.

서버는 공지 수정에 ETag/If-Match 조건을 제공하지 않는다. 사전 조회와 변경 필드만 전송하는 방식으로 불필요한 덮어쓰기를 줄이지만 GET과 PATCH/DELETE 사이에 발생하는 변경까지 원자적으로 막는 계약은 없다. 클라이언트에서 버전 필드나 헤더를 임의 추가하지 않았다.

## 결과·실패·이탈

서비스와 화면에서 중복 처리를 직렬화한다. 네트워크·타임아웃·5xx·잘못된 성공 응답은 정확한 공지 ID를 다시 읽는다. 저장 내용이 확인되면 현재 결과를 반영하고, 내용이 달라졌으면 재확인을 요구한다. 삭제 응답 유실 후 현재 권한을 확인하고 공지를 조회할 수 없으면 “더 이상 조회할 수 없음”으로 안내하며 내가 삭제했다고 추정하지 않는다. 204 삭제 응답을 받은 경우에만 삭제 완료로 표시한다.

아직 기존 내용이거나 재조회를 완료하지 못하면 저장·삭제를 잠근다. `수정 상태 다시 확인`은 읽기만 하고 PATCH/DELETE를 자동 반복하지 않는다. 작성한 내용을 버리고 서버 원본으로 돌아갈 때는 별도로 확인한다. 처리 결과가 나중에 확인되면 초안과 현재 서버 상태를 맞추고 잠금을 해제한다. 권한 상실·인증 만료와 삭제된 공지는 기존 내용을 내린다.

초안과 미확정 변경 요청을 API 모드의 AsyncStorage에 캐시하지 않는다. 재실행은 서버의 현재 공지를 읽으며 쓰기를 재전송하지 않는다. 작성 중 이탈은 확인하고 저장·삭제 중 이탈은 막는다. 목록 복귀 시 현재 부원 자격·동아리 선택 저장을 확인하고 기존 목록을 새로 읽어 제목·분류·고정 순서와 읽지 않은 수를 반영한다.

## Mock과 검증

기존 `@tamagochi/mock-notice-content/v1`을 확장했다. `notices`는 새 공지와 기본 공지 수정 내용을 ID별로 합치는 목록이고, 선택 필드 `deleted`는 삭제한 공지의 동아리·공지 ID 목록이다. 이전 v1 기록도 그대로 읽는다. 등록 서비스도 삭제 목록을 보존하므로 새 글을 쓴 뒤 기본 공지가 다시 생기지 않는다. 읽음 기록, 작성자, 생성일과 기존 알림 상태는 유지한다. 다른 동아리와 공부·상점·가입 신청 기록은 수정하지 않는다. 저장 실패·손상 시 기존 내용을 지우거나 성공으로 확정하지 않는다.

타입·린트와 총 186개 테스트가 통과했다. 새 20개는 권한 선확인·정확한 공지, 변경 필드·null 해제·입력 검증, 읽음·알림 보존, 충돌·중복 요청, 확정 거절·응답 유실·잘못된 영수증, 삭제 완료와 조회 불가의 구분, 권한 회수와 Mock 수정·삭제·저장 실패·삭제 목록 호환을 검증한다. API Android·iOS·Web과 Mock Web 내보내기도 통과했다.

격리 Chrome의 가짜 API로 관리 진입·일반 부원 차단, 작은 화면·상단 저장, 세부 분류 해제·고정, 새로고침·이탈·삭제 취소, 중복 저장, 다른 운영진의 수정과 삭제 확인 중 변경, 저장 응답 유실·늦은 재조회, 삭제 응답 유실, 권한 회수 시 확인창 제거·계정 전환·만료를 확인했다. 320·390·1280px를 확인했다.

Mock에서는 기본·새 공지 수정과 삭제 유지, 읽지 않은 수·분류·읽음 보존, 저장·삭제 실패 후 서버 내용 재확인, 새 등록 뒤 삭제한 기본 공지 미노출, 작성 결과 화면과 수정 내용 공유, 동아리 격리와 공부 기록 보존을 확인했다. 공통 입력과 저장 형식 변경 후 기존 공지 작성의 API·Mock 브라우저 검증도 다시 통과했다. 운영 API 네트워크를 차단한 환경에서 수행했으며 운영 공지를 수정하거나 삭제하지 않았다. 실계정·실기기 키보드와 화면 읽기 검증은 별도다.

미리보기는 `http://localhost:8082/notice`에서 공지를 펼치고 `수정·삭제`를 누른다. Mock 첫 동아리의 기본 공지는 `/clubs/mock-club-study/notices/mock-club-study-reading/edit`로 직접 열 수도 있다. 실제 API에서는 작성 권한이 있는 계정이 필요하다.
