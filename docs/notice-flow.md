# 가입 동아리 선택과 공지 조회

## 범위와 디자인

사용자의 공지 이미지와 기획 v4의 필터·공지 카드 구성을 기준으로 구현했다. 하늘색 배경, 게임 로고·Bolt, 큰 NOTICE 제목, 읽지 않은 전체 수, 가로 분류 필터와 흰색/네이비 카드, 분류·하위 분류·고정·NEW 표시를 반영했다. 날짜는 카드 위쪽, 작성자와 펼치기는 아래쪽에 두며 카드 머리 전체가 본문 펼치기 버튼이다. 긴 본문은 일반 UI 폰트로 표시한다.

`src/app/(tabs)/notice.tsx`는 기능 화면만 내보낸다. `features/notices/`에 화면·카드·필터·조회 훅을, 서비스·Mock·타입은 각각 해당 폴더에 둔다. API의 색상 이름은 공통 `constants/palette.ts`에서 매핑한다. 기존 카드·버튼·헤더·테마를 재사용하며 내비게이션 컴포넌트와 패키지는 변경하지 않았다.

이번 범위는 가입한 동아리 선택, 부원용 공지 목록·필터·본문·읽음·페이지 조회다. 후속 [동아리 가입 흐름](club-join-flow.md)에서 초대 코드 신청·취소와 승인 후 진입을 연결했다. [동아리 생성](club-create-flow.md)과 [가입 신청 관리](club-applications-flow.md)도 연결했으며, 현재 선택 동아리의 관리 버튼은 `applications.decide` 권한이 있을 때만 표시한다. [공지 작성](notice-compose-flow.md)과 [수정·삭제](notice-management-flow.md)는 `notices.write` 권한으로 연결했다. [분류·세부 분류 관리](notice-categories-flow.md)는 `noticeCategories.manage` 권한으로 연결했으며 Mock도 같은 동적 분류를 공유한다. 후속 [읽지 않은 수 배지](notice-unread-flow.md)를 하단 탭·동아리 칩에 연결했다. 기기 푸시 수신은 별도 준비가 필요하다. 가입하지 않았거나 신청만 대기 중인 동아리의 공지를 임의로 보여주지 않는다.

## 동아리 선택

`ClubProvider`를 계정별 게임 scope 안에 추가했다. 인증된 API 계정에 대해서만 부원 자격을 불러온다. 동아리 조회 중이거나 동아리가 없어도 Home·Study·Shop·Profile은 사용할 수 있다.

- `/clubs/-/members?userId=me&pageSize=200`의 모든 페이지에서 승인된 부원 자격을 찾고, 각 `/clubs/{clubId}`로 이름을 조회한다. 조회 중 삭제된 404 동아리는 제외한다. 목록 도중 실패하면 불완전한 목록을 성공으로 취급하지 않는다.
- 마지막 선택이 현재 목록에 있으면 복구하고, 없으면 첫 번째 가입 동아리를 사용한다. 동아리가 없으면 선택을 비우고 공지 화면에서 안내한다. 현재 소속 확인 전에는 로컬 ID만 믿고 공지를 요청하지 않는다.
- 선택 키는 `@tamagochi/club-selection/v1/{API 주소}/{사용자 ID}`다. Mock은 별도 `@tamagochi/mock-club-selection/v1`을 사용한다. 토큰·공지 본문을 이 키에 보관하지 않는다.
- 선택 저장 후에 새 동아리를 적용한다. 전환 중에는 이전 공지 화면을 제거하고, 저장 실패 시 이전 동아리로 돌아가 재선택을 안내한다. 존재하지 않는 저장 ID는 현재 소속으로 보정한다.
- foreground 복귀와 명시적인 동아리 목록 재확인으로 부원 자격을 다시 조회한다. 공부 데이터와 동아리 선택을 같은 저장소 레코드로 합치지 않는다.

## API 계약

Backend `98441b9`의 OpenAPI 0.1.0과 Members·NoticeCategories·Notices 컨트롤러, 공지 저장소와 페이지 요청 처리를 확인했다. 모든 요청은 기존 계정별 고정 Bearer 토큰 클라이언트를 사용한다.

| 요청 | 용도 |
| --- | --- |
| `GET /clubs/-/members?userId=me` | 내가 가입한 동아리의 부원 자격, 페이지당 최대 200 |
| `GET /clubs/{clubId}` | 선택용 동아리 이름·부원 수 |
| `GET /clubs/{clubId}/noticeCategories` | 동적 분류·세부 분류·색상 |
| `GET /clubs/{clubId}/members` | 공지 작성자 닉네임, 모든 페이지 조회 |
| `GET /clubs/{clubId}/notices?pageSize=50` | 고정 먼저, 각 그룹에서 최신 먼저인 서버 순서 유지 |
| 같은 목록의 `categoryId`, `subcategoryId`, `pageToken` | 분류별 목록과 다음 페이지 |
| `GET /clubs/{clubId}/notices?read=false&totalSize=true&pageSize=0` | 분류 필터와 무관한 동아리 전체의 읽지 않은 수 |
| `GET /clubs/{clubId}/notices/{noticeId}` | 펼칠 본문의 최신 상세 |
| `PUT /clubs/{clubId}/notices/{noticeId}/reads/me` | 본문을 펼쳤을 때 읽음 저장, 요청 본문 없음 |

ID·분류 색상·공지 필드·날짜·페이지 토큰·읽지 않은 수를 런타임 검증한다. 동아리·작성자 목록은 마지막 페이지까지 조회하고 같은 토큰의 반복은 오류로 처리한다. 다음 공지 페이지에는 같은 분류 필터를 유지하며 토큰을 인코딩한다. 필터 변경 시 첫 페이지부터 다시 조회한다. 경계에서 겹친 공지 ID는 중복 표시하지 않고 이미 확인된 읽음 상태를 유지한다.

작성자 이름은 현재 부원 목록의 `userId`로 매핑한다. `authorUserId: null`은 “탈퇴한 사용자”, 현재 목록에서 이름을 구할 수 없거나 작성자 필드가 없으면 “작성자 정보 없음”으로 구분한다. 일반 공지 날짜는 한국 달력 날짜이며 공부 정산의 오전 4시 경계를 적용하지 않는다. 본문은 일반 Text로 표시하며 HTML을 실행하지 않는다.

## 읽음·실패·격리

- 목록만 받거나 스크롤하는 동안에는 읽음을 전송하지 않는다. 머리를 눌러 상세를 받아 본문을 보여줄 때, 아직 읽지 않았다면 PUT한다.
- 상세 조회·읽음 저장 중 중복 탭을 막는다. PUT 실패 시 본문은 볼 수 있지만 NEW와 읽지 않은 수를 성공으로 바꾸지 않는다. “읽음 다시 확인”은 상세를 먼저 다시 읽는다.
- PUT 응답이 유실됐어도 재조회에서 읽음이 확인되면 추가 PUT 없이 복구한다. 읽음이 확인된 후 전체 수를 다시 GET한다. 수 조회만 실패하면 숫자를 확정해서 보여주지 않고 새로고침을 안내한다.
- 페이지 추가 실패는 현재 목록과 토큰을 유지해 재시도한다. 접근 권한이 바뀐 404 응답에서는 해당 목록/본문을 비우고 동아리 재확인을 안내한다.
- 동아리 전환은 게시판 인스턴스를 새로 만든다. 계정 전환은 기존 게임 scope 전체를 폐기한다. 지연된 상세·페이지·읽음 응답을 새 동아리나 다른 계정에 적용하지 않는다.
- 새로고침과 화면 재진입 때 다시 조회한다. 실시간 공지 push나 오프라인 본문 캐시는 구현하지 않았다.

## Mock과 검증

Mock은 기본 가입한 두 동아리와 가입 흐름에서 승인된 동아리의 동적 분류·세부 분류·공지를 제공한다. 신청 중이거나 탈퇴한 동아리는 포함하지 않는다. 기본 부원 자격의 읽은 ID는 `@tamagochi/mock-notice-reads/v1`, 신규 승인·재가입 자격은 `@tamagochi/mock-notice-reads/v2/{clubId}/{memberId}`에 저장한다. 새 자격에 이전 읽음이나 데모의 읽음 표시를 적용하지 않는다. 기존 공부/목표/상점 기록을 초기화하지 않는다. 손상된 읽음 기록은 오류로 알리고 자동 삭제하지 않는다. 같은 공지의 읽음을 반복 저장해도 중복 추가하지 않는다. API 실패를 이 Mock으로 대체하지 않는다. 탈퇴 후 목록·선택 정리는 [강퇴·탈퇴 흐름](club-membership-removal-flow.md)을 따른다.

후속 공지 작성의 `@tamagochi/mock-notice-content/v1`을 같은 목록에 합쳐 고정·날짜 순으로 정렬하고, 분류 필터와 읽지 않은 수·읽음 처리에도 반영한다. 새 동아리도 작성한 공지만 표시하며 다른 동아리의 글을 섞지 않는다.

`npm.cmd run typecheck`, `npm.cmd run lint -- --no-cache`, `npm.cmd test`가 통과했다. 총 85개 테스트에 이번 작업의 13개를 추가했다. 부원/작성자 페이지 조회, 동적 분류, 읽지 않은 전체 수 쿼리, 필터·커서, 상세와 읽음 요청의 분리, 잘못된 응답과 날짜·작성자 처리, Mock 읽음 보존·저장 실패를 검증했다.

격리된 Chrome에서 API 계약 응답을 주입해 인증 전 요청 제한, 가입 목록 복구, 분류·세부 분류와 빈 결과, 읽음 저장 실패·재시도·응답 유실, 수 재조회 실패, 다음 페이지 재시도, 동아리 전환 중 늦은 상세 응답, 선택 저장 실패와 잘못된 저장 ID, 접근 철회·빈 동아리·다른 계정·인증 만료를 확인했다. 320·390·1280px에서 가로 넘침과 카드 배치를 확인했다. 운영 계정이나 공지·읽음 상태는 변경하지 않았다.

Mock 브라우저에서도 읽음 저장 실패 후 복구·새로고침·동아리별 읽음 독립·선택 복원·세부 분류를 확인했다. Home → Study → 결과 → Home → 공지에서 공부 결과와 읽음 기록이 각각 보존되며 API 호출이 없었다. Android·iOS·Web 번들 생성도 통과했다.

실제 인증된 부원 계정·운영 공지와 여러 실기기의 읽음 동기화, 화면 읽기·긴 목록 성능 검증과 최종 방 에셋은 남아 있다. 기존 Metro 개발 SSR 오류는 후속 [안정화 작업](metro-dev-stability.md)에서 수정했다.

## 미리보기

```powershell
$env:EXPO_PUBLIC_DATA_MODE='mock'
npx.cmd expo export --platform web --output-dir .expo/preview
npx.cmd expo serve .expo/preview --port 8082
```

같은 PC에서 `http://localhost:8082/notice`로 접속한다. 실제 API 모드는 `EXPO_PUBLIC_DATA_MODE=api`로 다시 내보내고 로그인해야 하며, 승인된 동아리 부원 자격이 있어야 공지가 보인다.
