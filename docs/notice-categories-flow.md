# 공지 분류·세부 분류 관리

## 화면과 권한

2026-11-03(KST)에 Backend `98441b9`의 OpenAPI 0.1.0, NoticeCategories 컨트롤러·저장소·라벨 도메인·e2e와 Prisma 관계를 확인했다. 기존 공지의 색상별 분류 칩, 하늘색 배경, 크림색 카드, 네이비 외곽선과 노란 주요 버튼을 재사용한다. 공통 `GameColorPicker`와 색상 라벨을 분리했으며 새 에셋이나 패키지는 추가하지 않았다.

공지 화면의 `공지 분류 관리`는 해당 동아리의 `noticeCategories.manage` 권한으로 표시한다. `notices.write`나 `applications.decide`만으로는 관리할 수 없다. 버튼 클릭·화면 진입·foreground 복귀·변경 직전·변경 결과 확인 때 현재 권한을 다시 읽는다. `/clubs/{clubId}/notice-categories`는 인증이 필요한 루트 Stack 화면으로 하단 탭은 없다. 권한 상실 시 목록·입력·열린 삭제 확인창을 제거한다. 기존 계정 scope와 고정 Bearer 클라이언트를 사용해 다른 계정의 늦은 응답을 적용하지 않는다.

새 분류에는 이름과 여덟 가지 계약 색상을 선택하며, 각 분류 아래에서 세부 분류 이름을 추가한다. 이름은 앞뒤 공백을 제거한 1~10 grapheme cluster다. `Intl.Segmenter`가 없는 런타임에서는 최대 길이를 서버가 검증한다. 같은 동아리의 분류 이름, 같은 분류 안의 세부 분류 이름은 각각 중복될 수 없다. 다른 분류의 세부 분류에는 같은 이름을 사용할 수 있다.

## API와 삭제 제약

| 요청 | 용도 |
| --- | --- |
| `GET /clubs/{clubId}/members/me/permissions` | 정확한 관리 권한 확인 |
| `GET /clubs/{clubId}`, `/noticeCategories` | 현재 동아리·분류·색상·기본 여부·세부 분류 |
| `POST /clubs/{clubId}/noticeCategories` | `{ name, color }`로 분류 추가 |
| `DELETE /clubs/{clubId}/noticeCategories/{categoryId}` | 본문 없이 분류와 그 세부 분류 삭제 |
| `POST /clubs/{clubId}/noticeCategories/{categoryId}/subcategories` | `{ name }`으로 세부 분류 추가 |
| `DELETE /clubs/{clubId}/noticeCategories/{categoryId}/subcategories/{subcategoryId}` | 본문 없이 세부 분류 삭제 |

기본 여부는 이름이 아닌 서버의 `preset`으로 판별한다. 기본 전체공지에는 분류 삭제 버튼을 표시하지 않으며 세부 분류 추가는 허용한다. 사용 중인 분류·세부 분류는 서버가 409 `in-use`로 거절한다. 일반 분류 삭제는 하위 분류도 함께 삭제하므로 확인창에서 이를 안내한다. 이름 변경·색상 수정·재정렬 계약은 없어 추가하지 않았다.

삭제 확인 시 대상의 원본을 보관하고, 실행 직전 최신 목록과 비교한다. 확인 중 이름·색상·기본 여부·하위 목록이 달라졌다면 DELETE 없이 다시 확인하도록 한다. 이미 없는 항목은 추가 DELETE 없이 현재 목록을 반영한다. 서버에는 ETag나 조건부 삭제 계약이 없으므로 사전 조회 이후 발생하는 동시 변경까지 원자적으로 막지는 못한다.

## 결과 확인과 실패

서비스와 화면에서 중복 탭을 직렬화한다. 추가·삭제 뒤 목록을 다시 읽어 실제 상태를 확인한다. 409 `duplicate-name`, `preset`, `in-use`와 확정된 거절은 입력을 유지하고 최신 목록을 확인한다. 네트워크·타임아웃·5xx·잘못된 성공 응답에서는 쓰기를 반복하지 않고 조회만 수행한다. 삭제 404도 현재 접근 권한과 목록을 다시 확인한다.

추가한 이름·색상이 있거나 삭제 대상이 없는 상태가 확인되면 중립적인 “현재 목록에서 처리 상태를 확인했어요”를 표시한다. 다른 운영진이 같은 상태를 만들 수 있으므로 내가 처리했다고 추정하지 않는다. 재조회로도 결과를 확인하지 못하면 입력을 보존하고 변경 기능을 잠근다. `분류 목록 다시 확인`은 GET만 수행한다. 새 목록을 확인한 뒤 결과를 검토해 명시적으로 다음 작업을 선택하며, 자동 POST/DELETE 재시도는 없다. 명시적 재시도도 최신 목록과 서버의 이름 중복 제약을 다시 거친다.

API 모드의 입력·미확정 요청·분류 본문은 AsyncStorage에 캐시하지 않는다. 재실행은 현재 목록만 읽고 쓰기를 재전송하지 않는다. 화면을 벗어나면 저장하지 않은 짧은 이름 입력은 유지하지 않는다. `공지 목록으로` 버튼은 현재 소속과 동아리 선택 저장을 확인한 뒤 이동한다. 공지 목록·작성·수정은 재조회한 동적 분류를 공유하며, 삭제된 분류는 재선택하도록 한다.

## Mock과 검증

Mock은 `@tamagochi/mock-notice-categories/v1`에 `{ version: 1, clubs: { [clubId]: categories } }`를 저장한다. 기록이 없는 기존 동아리는 이전 기본 분류를, 새로 만든 동아리는 전체공지 하나를 제공한다. 조회만으로 초기 데이터를 쓰지 않는다. 공지 목록·작성·수정·관리 서비스가 같은 분류 저장소를 읽으며, 실제 활성 공지의 참조를 확인해 사용 중인 삭제를 거절한다. 사용하지 않는 일반 분류는 하위 분류와 함께 삭제한다. 다른 동아리·공지 내용·읽음·공부 기록은 수정하지 않는다. 손상되거나 저장에 실패한 기록을 지우지 않는다.

첫 Mock 동아리와 생성한 동아리의 운영자는 분류 관리 권한이 있고, 일반 부원인 두 번째 동아리에는 없다. 이 권한은 공지 작성·가입 신청 처리와 독립적으로 검사한다. API 오류를 Mock으로 자동 대체하지 않는다.

타입·린트와 총 206개 테스트가 통과했다. 새 20개는 정확한 권한·DTO, 입력과 중복 범위, 요청 경로·본문, 기본·사용 중·변경된 대상의 삭제 제한, 중복 처리, 응답 유실·잘못된 응답·늦은 재조회·삭제 404·권한 회수, Mock 공유·저장 실패·손상 보존을 검증한다. API Android·iOS·Web과 Mock Web 내보내기도 통과했다.

격리 Chrome의 가짜 API에서 추가·세부 분류·중복 탭, 삭제 취소·사용 중 거절·확인 중 하위 변경·하위 동시 삭제, 목록/작성과 공유, 응답 유실·잘못된 응답·조회 실패 후 수동 복구, 권한 회수 시 확인창 제거·계정 전환·인증 만료를 확인했다. Mock에서는 재실행 후 유지, 새 분류로 공지 작성·수정·삭제 후 사용 제한 해제, 저장 실패 후 재확인, 일반 부원 차단·새 동아리 운영자·동아리 격리·공부 기록 보존을 확인했다. 320·390·1280px에서 가로 넘침을 확인하고 기존 공지 수정·삭제의 API 검증과 공지 작성의 Mock 검증도 다시 통과했다.

모든 브라우저 검증은 운영 API 네트워크를 차단하고 수행했다. 실계정·실기기 키보드와 화면 읽기 검증은 별도다.
