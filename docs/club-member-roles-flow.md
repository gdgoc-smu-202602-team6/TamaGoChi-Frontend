# 부원 목록·역할 관리

## 화면과 권한

2026-11-04(KST)에 Backend `98441b9`의 Roles·Members 컨트롤러, Member/ClubManagers 도메인과 e2e, OpenAPI 0.1.0을 확인했다. 기존 동아리 관리 시안의 크림색 부원 카드·색상별 파트 표시·네이비 테두리·노란 주요 버튼을 사용한다. 역할 선택은 같은 게임 카드의 확인창이며 긴 권한 목록은 스크롤한다. 새 패키지나 에셋은 추가하지 않았다.

공지·마이의 현재 동아리와 동아리 기본 설정에서 `부원·역할 관리`를 연다. 진입은 정확한 `members.manage` 권한으로 검사한다. 다른 관리 권한만으로는 버튼을 표시하지 않는다. 클릭·화면 진입·foreground 복귀·변경 직전·결과 확인 때 현재 권한을 다시 읽는다. `/clubs/{clubId}/members`는 인증이 필요한 루트 Stack 화면이며 하단 탭은 없다.

부원 카드는 닉네임·내 부원 표시·가입일·파트·역할을 표시한다. 역할 변경 버튼으로 대상 부원과 현재 역할, 서버가 제공한 역할 목록과 선택한 역할의 권한을 확인한 뒤 변경한다. 권한 판별에 `운영진`, `Admin` 같은 이름을 사용하지 않는다. 강퇴·동아리 탈퇴·내 파트/알림 설정은 다음 작업 범위다.

## API와 변경 확인

| 요청 | 용도 |
| --- | --- |
| `GET /clubs/{clubId}/members/me/permissions` | 현재 `members.manage` 확인 |
| `GET /clubs/{clubId}`, `/parts` | 동아리 이름과 동적 파트 |
| `GET /roles` | 서버 역할 ID·이름·권한 |
| `GET /clubs/{clubId}/members/me` | 현재 계정의 부원 자격 |
| `GET /clubs/{clubId}/members?pageSize=200` | 모든 페이지를 서버 순서대로 읽음 |
| `PATCH /clubs/{clubId}/members/{memberId}` | `{ roleId }`만 변경 |

멤버 ID와 사용자 ID를 구분하며, 토큰은 기존 계정별 고정 클라이언트를 사용한다. 목록의 페이지 토큰을 인코딩하고 반복 토큰·중복 부원/사용자·다른 동아리의 응답·알 수 없는 역할/파트·일치하지 않는 내 부원 자격은 불완전한 성공으로 표시하지 않는다. 다른 부원의 이메일이나 사용자 상세는 별도로 조회하지 않는다.

확인창은 열었을 때의 부원 원본을 유지한다. 변경 직전에 대상의 계정·가입일·닉네임·파트·역할과 선택한 역할의 이름·권한을 다시 확인한다. 대상이 없거나 내용이 달라졌으면 PATCH 없이 다시 선택하도록 한다. 이미 원하는 역할이면 추가 PATCH 없이 현재 목록을 반환한다. 파트·알림·중첩 role 객체는 요청에 넣지 않는다.

마지막 `members.manage` 보유자의 권한을 해제하려는 409 `last-manager`는 다른 부원에게 먼저 관리 권한을 부여하도록 안내한다. 역할 이름이나 임의의 직급 서열로 변경 대상을 제한하지 않는다. 서버의 권한과 마지막 관리자 제약을 따른다. 회원 변경에는 ETag·If-Match 계약이 없어 사전 조회 이후의 동시 변경까지 원자적으로 막지는 못한다.

## 오류·본인 역할 해제·격리

화면과 서비스가 중복 요청을 직렬화한다. 성공 응답의 대상·계정·가입일·역할을 검증하고 현재 권한과 목록을 다시 확인한다. 확정된 4xx는 재전송하지 않는다. 네트워크·타임아웃·5xx·잘못된 성공 응답은 실제 부원의 현재 역할을 조회한다. 확인되면 “현재 목록에서 역할 상태를 확인했어요”로 표시하며 누가 변경했는지는 추정하지 않는다.

결과가 불확실하면 마지막 목록을 읽기 전용으로 유지한다. `부원 목록 다시 확인`은 GET만 전송한다. 재조회 후 사용자가 현재 상태를 검토하고 작업을 명시적으로 다시 선택하며 PATCH를 자동 반복하지 않는다. 목록·역할 초안·미확정 요청은 API 모드의 AsyncStorage에 캐시하지 않고 재실행 때도 읽기만 수행한다.

본인 역할 변경으로 관리 권한을 잃을 수 있다. PATCH 응답이 유실됐어도 권한 재조회에서 `members.manage`가 없으면 “현재 계정의 관리 권한이 바뀌었어요”로 안내하고 목록·열린 역할 창을 내린다. 이때 원하는 역할이 적용됐다고 추정하거나 접근할 수 없는 관리 목록을 계속 요청하지 않는다. 외부 권한 회수·인증 만료·계정 전환에서도 이전 계정의 목록을 제거한다. 공지로 복귀하면 각 관리 진입이 현재 권한을 다시 검사한다.

초기 로딩과 권한 회수로 목록이 비어 있는 상태에서도 목록 행이 부원 자격을 참조하지 않도록 검사한다. `◀ 공지`와 `공지 목록으로`는 현재 소속과 동아리 선택 저장을 확인한 뒤 이동한다.

## Mock과 검증

Mock은 동아리별 부원 목록과 두 역할(전체 관리 권한·일반 부원)을 제공한다. 첫 동아리와 새로 생성한 동아리의 나는 초기 관리자다. 두 번째 동아리와 승인 후 가입한 동아리에서 나는 일반 부원이고 다른 관리자가 있다. 생성자는 선택한 파트, 승인된 부원은 실제 신청 파트·닉네임·승인 시각을 사용한다.

역할 변경만 `@tamagochi/mock-member-roles/v1`의 `{ version: 1, clubs: { [clubId]: { [memberId]: roleId } } }`에 저장한다. 조회만으로 초기 데이터를 쓰지 않는다. 부원 ID가 동아리 사이에 같아도 변경은 동아리별로 격리한다. 모든 기존 Mock 관리 서비스의 권한도 이 역할에서 계산한다. 본인이 내려놓은 권한은 재실행 후에도 유지되며 다른 관리 기능으로 우회할 수 없다. 파트 삭제 제한도 같은 실제 Mock 부원 목록을 참조한다. 역할 변경은 부원 자격·공부·공지·초대 코드·신청 기록을 수정하지 않는다. 저장 실패·손상 시 기존 기록을 지우지 않는다.

타입·린트와 총 264개 테스트가 통과했다. 새 20개는 정확한 권한·전체 페이지·DTO·역할/파트 관계, 정확한 PATCH·중복·원본/역할 정의 충돌, 마지막 관리자·확정 거절·응답 유실·잘못된 응답·늦은 재조회·본인 권한 해제, Mock 저장·전체 관리 권한 연동·신규 승인 부원·생성자·손상/기존 데이터 보존·파트 삭제 참조를 검증한다. API Android·iOS·Web과 Mock Web 내보내기도 통과했다.

격리 Chrome의 가짜 API로 인증 제한·페이지 조회·역할 권한 미리보기·취소·중복 탭·서버의 추가 역할·지정/해제·마지막 관리자·확인 중 외부 변경·응답 유실·잘못된 성공 응답·조회 실패 후 수동 확인·본인 권한 해제 응답 유실·외부 권한 회수·계정 전환·만료를 확인했다. 320×568·390×844·1280×844 화면에서 가로 넘침과 스크롤 후 확인/취소 버튼 접근을 확인했다.

Mock에서는 전체 부원 목록·역할 변경 유지·저장 실패·재확인, 공지/마이/기본 설정 진입, 실제 승인된 신규 부원 표시, 본인 해제 후 다른 관리 버튼 제거, 일반 부원 제한·새 동아리 생성자·동아리 격리·공부 기록 보존을 확인했다. 공유 Mock 변경 후 기존 파트 추가/삭제·승인 대기 참조·가입 선택 브라우저 검증도 통과했다. 운영 API 네트워크를 차단해 운영 계정의 역할을 변경하지 않았다. 실계정·실기기 화면 읽기·여러 운영진의 동시 처리 검증은 별도다.
