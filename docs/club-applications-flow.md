# 운영진의 가입 신청 관리

## 화면과 범위

2026-11-03(KST)에 Backend `98441b9`의 OpenAPI 0.1.0, 신청·권한 컨트롤러와 도메인 계약을 확인했다. 기획 v4 `24-club-settings`의 동아리 요약, 대기 인원 배지, 신청자 이름·이메일·파트, 카드 안의 승인·거절 버튼을 참고했다. 공통 하늘색 배경, 네이비 테두리, 크림색 요약 카드와 초록 승인 버튼을 사용한다. 전체 운영진 설정을 한꺼번에 구현하지 않고 가입 신청 처리만 추가했다.

가입·신청의 동아리 카드, 공지와 마이의 현재 선택 동아리에서 `가입 신청 관리`를 연다. `/clubs/{clubId}/applications`는 인증이 필요한 루트 Stack 화면이며 하단 탭은 없다. `applications.decide` 권한이 있어야 버튼을 표시하고, 직접 주소로 들어와도 같은 권한을 확인한 뒤 신청자 정보를 요청한다. 다른 운영 권한만으로는 신청 관리를 허용하지 않는다.

화면은 동아리 이름·부원 수·파트 수·전체 대기 신청 수, 이름·이메일·파트·신청일을 표시한다. 파트 이름·색상은 서버 데이터이며 신청자는 고정 예시가 아니다. 계정 정보가 비어 있는 응답에는 중립적인 대체 문구를 사용한다. 처리가 끝난 신청은 대기 목록에서 빠지고, 목록이 비면 빈 상태를 표시한다.

## API와 처리 결과

| 요청 | 용도 |
| --- | --- |
| `GET /clubs/{clubId}/members/me/permissions` | 진입·목록 조회·처리 직전의 현재 권한 확인 |
| `GET /clubs/{clubId}`, `/parts` | 동아리 요약과 현재 파트 목록 |
| `GET /clubs/{clubId}/applications?state=PENDING&pageSize=200` | 모든 페이지를 조회해 대기 목록 구성 |
| `GET /clubs/{clubId}/applications/{applicationId}` | 처리 직전과 불확실한 응답 이후의 정확한 신청 상태 |
| `PATCH /clubs/{clubId}/applications/{applicationId}` | 본문 `{ state: 'APPROVED' 또는 'REJECTED' }`만 전송 |

페이지 토큰은 인코딩하며 반복 토큰·중복 ID·다른 동아리 신청·대기 중이 아닌 목록 항목·잘못된 응답은 오류로 처리한다. 신청자 연락처와 권한은 API 모드의 AsyncStorage에 캐시하지 않는다. 기존 계정 scope와 고정 Bearer 토큰을 사용한다.

중복 탭은 화면과 서비스에서 직렬 처리한다. PATCH 전에 권한과 정확한 신청을 다시 읽으며, 이미 결정된 신청은 변경하지 않고 실제 상태를 반환한다. 조회 직후 다른 운영진이 처리한 `409 not-pending`도 실제 결과를 다시 읽는다. 취소·삭제된 신청은 다시 처리하지 않는다. 승인에 따른 부원 생성과 역할 배정은 서버 책임이며 클라이언트에서 별도 부원 생성 API를 호출하지 않는다.

네트워크·타임아웃·5xx·잘못된 성공 응답 이후에는 GET으로 상태를 확인한다. 확인한 승인 또는 거절 상태를 표시하며, 어느 운영진이 처리했는지 추정하지 않는다. Backend는 결정 저장 후 알림 전송을 기다리므로 알림 단계의 오류가 이미 저장된 결정을 되돌렸다고 가정하지 않는다. 화면에서도 푸시 발송 성공을 주장하지 않는다.

처리 후 대기 목록·부원 수를 다시 읽고 공통 동아리 목록을 갱신한다. 낙관적으로 신청을 지우거나 부원 수를 증가시키지 않는다. 처리 결과나 후속 목록을 확인할 수 없으면 승인·거절을 비활성화하고 `신청 상태 다시 확인`을 제공한다. 이 버튼은 읽기만 하며 PATCH를 자동 반복하지 않는다. 권한 없음·동아리 접근 상실·인증 만료가 확인되면 표시 중인 신청자 정보도 내린다.

목록은 화면 진입, 앱 활성화, 직접 새로고침으로 갱신한다. 자동 폴링은 추가하지 않았다. 마지막 권한 확인 이후의 변경은 서버가 다시 검사한다.

## Mock 미리보기

`EXPO_PUBLIC_DATA_MODE=mock`에서 첫 동아리 `함께 공부하는 모임`과 직접 생성한 동아리에만 관리 권한이 있다. `픽셀 메이커스`는 일반 부원이다. 첫 동아리에는 미리보기 사용자와 구분되는 두 외부 신청자가 있다. 새로 만든 동아리의 대기 목록은 비어 있다.

결정은 `@tamagochi/mock-club-reviews/v1`에 저장한다. 승인된 외부 신청자는 가입·초대 코드 조회와 관리 화면의 부원 수에 함께 반영되고, 거절은 인원을 늘리지 않는다. 미리보기 사용자의 `MORI2026` 신청을 자동 승인하거나 본인에게 승인 버튼을 제공하지 않는다. 기존 공부·상점·내 가입 신청 기록은 변경하지 않는다. 저장소 실패·손상 시 기존 기록을 지우거나 성공을 표시하지 않는다.

```powershell
$env:EXPO_PUBLIC_DATA_MODE='mock'
npx.cmd expo export --platform web --output-dir .expo/preview
npx.cmd expo serve .expo/preview --port 8082
```

`http://localhost:8082/clubs/mock-club-study/applications`에서 로그인 없이 미리 볼 수 있다. API 모드는 `EXPO_PUBLIC_DATA_MODE=api`로 다시 빌드하고 실제 `applications.decide` 권한이 있는 계정으로 로그인한다.

## 검증과 남은 범위

타입 검사·린트와 총 148개 테스트가 통과했다. 새 17개는 권한 선확인, 동적 파트·전체 페이지, 잘못된 응답, 정확한 요청 본문, 권한 회수·취소, 동시·반대 결정, 응답 유실·알림 단계 500, 불확실한 결과, Mock 역할·저장 실패·재실행·부원 수와 기존 기록 보존을 검증한다. API 모드 Android·iOS·Web과 Mock Web 내보내기도 통과했다.

2026-11-03(KST)에 승인된 별도 프로필의 숨김 Chrome에서 수정 후 클릭 검증을 통과했다. 가짜 API 응답으로 첫 진입·전체 페이지 조회, 가입·신청/공지/마이의 관리 진입, 일반 부원의 직접 주소 차단, 중복 클릭, 다른 운영진의 결정·신청 취소, 응답 유실·알림 단계 500, 불확실한 결과의 버튼 잠금·조회 복구, 권한 회수·계정 전환·인증 만료를 확인했다. 최초 진입의 빈 목록 처리 오류도 재현되지 않았다. 320·390·1280px에서 가로 넘침과 화면 배치를 확인했다.

Mock에서는 승인·거절 저장과 새로고침 후 복구, 가입 목록·초대 코드 조회의 부원 수 공유, 저장 실패 후 조회 복구, 일반 부원과 새 동아리 생성자의 권한, 기존 공부·내 가입 신청 기록 보존을 확인했다. API 모드 검증에는 가짜 응답만 사용하고 브라우저에서도 운영 API 네트워크를 차단했다. Mock의 운영 API 호출도 0회였다. 실제 운영 신청 승인·거절, 푸시 수신, 실기기 화면 읽기·뒤로가기 검증은 수행하지 않았다.
